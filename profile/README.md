<h2>一、先做减法：把不满足硬条件的排除</h2>
<p>比较之前先排除，能省掉大量无效对比。硬条件通常只有三四条，但每一条都是“缺了就干不了活”。</p>
<h3>第一条：出口能不能固定</h3>
<p>需要长期登录同一账号的业务，必须能锁定出口地址。只提供轮换池的产品，无论单价多低都不适配。</p>
<h3>第二条：能不能开子账号</h3>
<p>三人以上协作就需要分权。没有子账号体系的，意味着密钥要共享，出问题无法定位到人。</p>
<p>第三条是扣费口径：至少在控制台要能看到每条出口的用量、每次替换的计费记录。账单只有一个总额的，月底对账会非常痛苦。三条都过了，再进到能力比较；硬条件不满足的产品，后面功能再漂亮也用不上。</p>

<h2>二、接口能力：五个必测动作</h2>
<p>宣传页上的“完善 API”不具备信息量。拿试用额度跑五个动作，能测出八成真实水平。</p>
<h3>动作一：列出口并带元数据</h3>
<p>调列表接口，看返回里有没有城市、ASN、当前状态、绑定的分组。只有 IP 和端口的，说明后端数据很薄，后面做分组管理会很吃力。</p>
<h3>动作二：切换出口并等待生效</h3>
<p>发起切换后轮询状态，记录从提交到生效的耗时。这个数字决定了故障时你的恢复速度，超过 5 分钟的产品要慎重。</p>
<h3>动作三：查单条用量</h3>
<p>按出口维度查流量与时长。只能查总量的产品，做不了成本归集。</p>
<h3>动作四：错误处理</h3>
<p>故意传错参数，看错误码是否区分类型、返回体里有没有可读的说明。全部返回 500 的接口，脚本没法做重试判断。</p>

<h2>三、节点质量：看数据不看宣传页</h2>
<p>节点质量由三件事决定：出口所属 ASN、同段邻居数量、以及上游带宽是否被超卖。</p>
<h3>ASN 与归属</h3>
<p>抽查三到五条出口，用公开查询入口看 ASN 类型是否为 isp、org 是否为当地运营商。如果多条出口落在同一个 hosting 段，说明所谓住宅只是转售机房资源。</p>
<h3>邻居密度要主动问</h3>
<p>问“这个 /24 目前有多少客户在用”，愿意给具体数字的服务商通常更有底气。答“我们做了隔离”的，往往就是共享池。</p>

<h2>四、故障恢复：SLA 之外的三个追问</h2>
<p>99.9% 这种数字意义有限，真正影响你的是故障发生后的处置方式。</p>
<h3>追问一：有没有独立状态页</h3>
<p>状态页要能看到历史事件，而不只是当前绿灯。有历史记录的服务商，说明他们把故障当工程问题管理。</p>
<h3>追问二：替换是自动还是人工</h3>
<p>出口异常时能否自助替换，决定了凌晨三点你能不能自己解决。需要提交工单等审核的，实际恢复时间以小时计。</p>
<p>最后一个问题是赔偿：按不可用时长折算，还是只给延长服务期，两种方式对现金流的影响不同，签合同前写清计算口径。这三问都能给出具体答案的，通常才是把稳定性当回事的团队。</p>

<h2>五、签约前的决策清单</h2>
<p>把上面几步的结论落成一张表，逐项打勾，比凭印象拍板可靠。</p>
<h3>必答的八项</h3>
<p>出口能否固定、是否独享、ASN 类型、替换额度与冷却期、子账号数量、API 是否可编程切换、故障响应方式、以及退款条款。八项里有两项含糊，就先把这家放到备选。</p>
<h3>留一条退路</h3>
<p>首期按最小规格月付，跑满一个计费周期再谈扩容。这样即使判断失误，损失也可控，而且能看到真实账单长什么样。</p>

<h2>常见问答</h2>
<h3>节点越多的平台越好吗？</h3>
<p>答：不是。覆盖国家数量与实际可用出口是两回事，很多小国只有一两条共享出口。先确认你要用的那两三个国家有没有独享资源。</p>
<h3>API 支持批量切换重要吗？</h3>
<p>答：出口超过十条时才明显重要。少量出口用控制台点几下也够，但批量场景下没有幂等接口会很容易出错。</p>
<h3>免费试用的平台值得试吗？</h3>
<p>答：可以试，但要注意试用池与正式池常常不是同一批资源。用试用得出的延迟结论，最好在首月付费后再复核一次。</p>
<h3>能同时用两家平台做备份吗？</h3>
<p>答：可以，且是常见做法。关键是备份出口不要和主出口落在同一网段，否则上游一出问题两个一起挂。</p>
